1. OBJECTIF DU DOCUMENT
======================================================================

Ce document explique l'etat actuel du projet AgriLoop, le resultat attendu,
la repartition du travail entre les quatre membres et l'ordre dans lequel
nous allons programmer.

Il sert de reference commune avant toute implementation PHP ou base de
donnees. Nous devons le relire ensemble et valider les choix fonctionnels
avant de commencer les developpements.

AgriLoop est une plateforme web de mise en relation autour des surplus
agricoles et de l'economie solidaire :
- un producteur peut publier une offre de surplus ;
- une association peut s'enregistrer et proposer ou recevoir un don ;
- les utilisateurs peuvent laisser un avis et signaler un avis ;
- un producteur peut gerer ses parcelles et sa consommation d'eau ;
- un espace back-office permet a l'administrateur de suivre les donnees.

3. DIAGNOSTIC DE L'ETAT ACTUEL
======================================================================

Le projet est actuellement une maquette front-end, pas encore une
application dynamique.

Ce qui fonctionne deja visuellement :
- la charte graphique AgriLoop est coherente sur les pages front-office ;
- les formulaires ont des labels, des champs obligatoires et un affichage
  responsive ;
- la page des dons du back-office contient une navigation, des statistiques,
  un filtre visuel et un tableau d'exemple ;
- la navigation contient deja les concepts principaux : Accueil, Offres,
  Dons, Parcelles, Avis et Back-office.

Ce qui n'est pas encore implemente :
- aucun fichier PHP applicatif dans le projet ;
- aucun controleur ni modele dans les dossiers correspondants ;
- aucune connexion a MySQL dans le projet ;
- aucune base ou script SQL AgriLoop ;
- les formulaires utilisent action="#" et ne sauvegardent rien ;
- les listes deroulantes contiennent des valeurs statiques ;
- les statistiques et les lignes du tableau sont des donnees fictives ;
- aucun CRUD, aucune validation serveur, aucune session, aucune authentification ;
- aucune page complete pour les modules Offres, Utilisateurs, Avis,
  Signalement, Parcelles et ConsommationEau.

Attention :
Le fichier de configuration fourni dans Downloads utilise la base
"travel". Il ne doit pas etre branche tel quel sur AgriLoop. Il faudra
creer une configuration dediee, sans exposer de mot de passe dans le code
public, et utiliser une base nommee par exemple "agriloop".

6. TRAVAIL COMMUN OBLIGATOIRE
======================================================================

Avant le developpement de chaque module, l'equipe doit valider :

1. La base de donnees et les noms exacts des tables et colonnes.
2. Les statuts autorises et leurs valeurs.
3. Les roles et les droits de chaque utilisateur.
4. Les pages qui sont accessibles sans connexion.
5. Les pages reservees a l'administrateur.
6. Le format des messages d'erreur et de succes.
7. La convention de nommage PHP, HTML, SQL et des fichiers.
8. La strategie de fusion des fichiers lorsque plusieurs personnes
   travaillent sur les memes vues ou le meme CSS.

Architecture recommandee :

- config/
  Connexion PDO et constantes de configuration.
- model/
  Classes metier et operations CRUD avec requetes preparees.
- controller/
  Reception des requetes, validation, appel des modeles et redirection.
- views/
  Formulaires, listes, details et messages.
- public/assets/ ou views/assets/
  CSS, images et scripts necessaires.

Le code doit respecter le principe :
formulaire -> controleur -> validation -> modele PDO -> base de donnees
-> redirection ou affichage d'un message.

======================================================================
9. RISQUES ET POINTS A CORRIGER
======================================================================

- Les pages actuelles sont statiques : une migration progressive vers PHP
  est necessaire sans casser la charte CSS.
- Les liens en # ne correspondent pas encore a de vraies pages.
- Les formulaires n'ont pas de traitement serveur.
- Le fichier de configuration fourni utilise une base "travel" et doit
  rester un exemple, pas une configuration de production AgriLoop.
- Les champs du diagramme doivent etre harmonises avant le SQL, notamment
  les accents dans les noms de champs, la distinction nom/prenom et les
  roles des utilisateurs.
- La suppression de donnees liees doit etre decidee : blocage si une
  relation existe ou suppression en cascade.
- Les mots de passe devront etre hashes avec password_hash et verifies
  avec password_verify.
- Toutes les requetes SQL devront utiliser des parametres PDO.
- Les statistiques du back-office devront etre calculees depuis la base,
  et non rester des nombres ecrits dans le HTML.
